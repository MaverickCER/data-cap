# Generated artifacts: what `data-cap` produces, and what it deliberately doesn't

This is the canonical place — for a human or an AI agent working in this
repository or a consuming project — to check before assuming `data-cap`
generates something it doesn't. Every artifact below is produced by
`generateDataArtifacts()` (or the `data-cap` CLI, its thin wrapper); nothing
here is generated by a separate, independently-derived pipeline. Concretely,
as of ADR 0054: `computeDataArtifacts` (the function both
`generateDataArtifacts` and `checkArtifacts` share) builds one
[`CapabilityInventory`](architecture.md#report-generation-model) and composes
it — together with the Dependency/Ownership/Finding/Change models below —
into one `EvidenceModel` every run, and every artifact in this file is a
projection of that same run's inventory/models, not a second, independently-
assembled source. `--evidence <path>` writes that composed model to disk
directly, as JSON, for a project that wants the canonical artifact itself
rather than only its Markdown/diagram projections.

**Every artifact in this table is evidence that can _support_ a review
process — a security review, a privacy review, a platform audit — never a
compliance claim.** Static analysis of one repository cannot, by itself,
establish compliance with any external standard. Every rendered artifact
that carries this claim opens with the same disclaimer
(`evidenceDisclaimer()` in `generated-banner.ts`):

> Machine-generated engineering artifact assembled from statically-provable
> code facts and author-declared documentation. It can support a security,
> privacy, or compliance review. It does not itself establish compliance
> with any standard.

## Declared vs. proven

Every fact in every generated artifact is one of exactly two kinds, and a
rendering function may never blend them or imply one is the other:

- **Declared** — metadata the author wrote via `documentData()`: `owner`,
  `category`, `sensitivity`, `protections`, `retention`, `purpose`,
  `legalBasis`, `dataResidency`, `auditRequired` (ADR 0051), `credentials`,
  `source`, `endpoints`, `metadata`. Presence is checked; correctness,
  adequacy, and enforcement are never claimed. A report may say a field's
  protections are _"documented"_, never that they are _"sufficient"_ or
  _"verified"_ — and, per ADR 0051, may say a legal basis was _"declared,"_
  never that it was _"determined valid."_
- **Proven** — facts derived by AST analysis of the actual source: an
  operation's literal `writes` shape, a `DependencyEdge` connecting a
  consuming file to a capability/field/operation. These are statically
  provable from the code that exists today, in this repository, at analysis
  time.
- **A third case, named explicitly because it's neither** —
  `evidence.fields[key].dynamicAccess` (ADR 0053) is declared, like every
  other governance field, but unlike every other one it's re-verified every
  run against a persisted content hash. A passing check establishes only
  that the citation is currently _supported by its own citation/integrity
  state_ — the cited file exists and hasn't visibly changed since the
  developer wrote it — never that the described access has been proven to
  happen there. No rendering of a `"declared-dynamic"` field ever uses
  "verified" or "proven" language for this reason.

See `AGENTS.md`'s numbered invariants 11–12 for the enforcement rule this
table's "Yes" column is built on: static analysis never infers a fact from
insufficient evidence, and a declared fact is never presented as proven.

## Canonical fact models (ADR 0050)

Seven canonical, versioned, JSON-serializable models — the machine-readable
surface a much larger catalog of named reports (Capability Inventory Report,
SARIF Security Findings Report, Data Migration Impact Report, and so on) is
derivable from, without `data-cap` building and maintaining each one as a
separate, independently-computed artifact. See
[ADR 0050](decisions/0050-fact-model-architecture.md) for the full
report → model mapping and the three requests cut on principle (Validator
Contract Report, a per-operation Cacheability Report, Executive Data
Architecture Report).

| Model                  | Builder                     | Schema                                                | What it answers                                                                                                                                                                                             |
| ---------------------- | --------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Capability Model       | `buildInventory`            | `@maverickcer/data-cap/schema/capability-model`       | Every discovered capability's fields and operations, active or not — `CapabilityInventory` itself, now versioned.                                                                                           |
| Dependency Model       | `buildDependencyModel`      | `@maverickcer/data-cap/schema/dependency-model`       | Every proven consumer relationship, indexed by capability and by consuming file (with per-access-site line numbers) — the fact `usage-report.ts`/`flow-graph.ts` project, computed once.                    |
| Ownership Model        | `buildOwnershipModel`       | `@maverickcer/data-cap/schema/ownership-model`        | The owner → {capabilities, fields} matrix — a versioned envelope around `buildOwnershipMatrix`.                                                                                                             |
| Finding Model          | `buildFindingModel`         | `@maverickcer/data-cap/schema/finding-model`          | Every finding, each with a structured, pre-computed `location` — the input a SARIF adapter or Evidence Model composes from.                                                                                 |
| Change Model           | `buildChangeModel`          | `@maverickcer/data-cap/schema/change-model`           | The manifest diff, plus an optional blast-radius index (which in-repo files currently consume each added/updated capability).                                                                               |
| Runtime Contract Model | `buildRuntimeContractModel` | `@maverickcer/data-cap/schema/runtime-contract-model` | `data-cap`'s own documented execution guarantees (concurrency, subscription sharing, dedup, atomic commit, cache/retry contracts) — package-scoped, not per-project, each fact traced to its governing ADR. |
| Evidence Model         | `buildEvidenceModel`        | `@maverickcer/data-cap/schema/evidence-model`         | The composition of the other six into one provenance-stamped artifact — what every Classification/Privacy/Retention/Audit/Compliance Evidence projection reads.                                             |

A first wave of reference projections ships alongside the models themselves
— `projectGetters`/`projectMutators`/`projectSubscriptions`/`projectFields`
(inventory-family filters), `renderDependencyGraphDot`/
`renderOwnershipGraphDot` (graph export), `buildSarifLog` (a SARIF 2.1.0
adapter over Finding Model), `buildOpenApiSchemaArtifact` (Capability
Model's fields as OpenAPI 3.1 `components.schemas`), and the
`project*Evidence` family built through `defineEvidenceProjection()`. Every
one of these is an ordinary consumer of the public model types above — none
has a privileged internal path a downstream tool couldn't also use.

## Explicitly deferred, with reasons

Nothing below is omitted silently. Each is deferred because building it now
would either require metadata this release deliberately didn't add (see
`specs/decisions/0049-capability-metadata-vocabulary.md`'s two
"deliberately not added" sections), or would imply an analysis `data-cap`
doesn't actually perform.

| Artifact                                      | Aligns with            | Why deferred                                                                                                                                                                                                                                                                                                                                                               |
| --------------------------------------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Threat Modeling Inputs                        | OWASP threat modeling  | Needs actual threat rules (attacker capability, mitigations, likelihood), not just an inventory — labeling bare inventory data "threat model" would imply analysis that hasn't been done.                                                                                                                                                                                  |
| Privacy Data Map (purpose-of-processing view) | NIST Privacy Framework | `purpose`/`legalBasis`/`dataResidency` are now modeled (ADR 0051), so the gap is no longer a missing dimension — it's that a dedicated renderer hasn't been built. Buildable today by a consumer projecting `purpose`/`legalBasis` off Capability Model directly, same as `projectClassificationEvidence`'s siblings; not shipped as a first-party report in this release. |
| OSCAL data-flow component                     | NIST OSCAL             | A real schema-conformance commitment, not a rendering choice — worth its own future ADR, not a rider on this one.                                                                                                                                                                                                                                                          |
| PCI DSS data-flow evidence                    | PCI DSS                | Only meaningful once a real deployment has cardholder-data fields to classify. The existing `sensitivity`/`metadata` vocabulary already supports someone building this today without a first-party PCI mode — `metadata: { regulatory: "PCI-DSS" }` is a documented, open convention, not a first-party taxonomy `data-cap` would have to validate.                        |
| SOC 2 evidence index                          | SOC 2 support artifact | SOC 2 has no single canonical data-flow document the way PCI/OWASP do — premature to design one before a real user needs it.                                                                                                                                                                                                                                               |
| Data Processing Register                      | Privacy governance     | Same as the Privacy Data Map above — the underlying fields exist (ADR 0051), no dedicated renderer ships in this release.                                                                                                                                                                                                                                                  |
| Full lineage through external systems         | Platform governance    | Structurally out of scope, not deferred — no static scan of one repository can know what a third-party system does with data after receiving it. `endpoints` documents the boundary; it can't see across it.                                                                                                                                                               |
| Validator Contract Report                     | Data contract evidence | `data-cap` has no per-field validator vocabulary by design (ADR 0039, `helpers/shape.ts` is structural type guards, not a validator system) — there is nothing to project this report from.                                                                                                                                                                                |
| Per-operation Cacheability Report             | Data contract evidence | `cache.ts` wiring lives inside an operation's opaque `execute` body — no declared vocabulary exists to statically answer "is this getter cached." The generic "how does `data-cap`'s cache module work" question is still answered by Runtime Contract Model (see ADR 0050).                                                                                               |
| Executive Data Architecture Report            | Executive reporting    | A single headline/grade is an opinion `data-cap` has no basis to assert on a consumer's behalf — the same reasoning `env-cap` ADR 0024 gives for cutting its own Executive Assurance Report. See ADR 0050.                                                                                                                                                                 |

## Jurisdiction-specific regulatory classification

`data-cap` does not ship a first-party GDPR/HIPAA/PCI/etc. taxonomy — those
mean different things in different deployments, and a tool analyzing one
repository can't know which regime applies. The existing, open
`CapabilityDocs.metadata`/`FieldDocs` extension bag is the documented
convention for recording this yourself, e.g. `metadata: { regulatory:
"GDPR,PCI-DSS" }`. `data-cap` never validates its contents.
