data-cap: a one-page brief

data-cap records who owns each piece of application data and how it may be handled. Lint and build checks compare that record with the code, and the data documentation is generated from it.

The problem

Different parts of an application each work out their own idea of whether data is loading, stale or changed. They disagree, and nobody owns the answer.

What it does

Each piece of data is declared once, with its owner, its fields and how each field may be handled. Checks in the editor and in CI compare the declaration with the code, and the documentation is regenerated from it.

Why it matters

  • Who owns each piece of data, and how it may be handled, is written once and checked against the code.
  • The data documentation is regenerated from the code, and a CI check fails when the committed copy is stale.
  • It works alongside the fetching and state libraries a team already uses.

What it costs

Adopting it means adding the package and declaring one piece of data at a time. It is free, open source software under the MIT licence, and it replaces no existing library.

What could go wrong

  • data-cap is pre-1.0. Per VERSIONING.md, a minor release may still change a Stable API before 1.0, so pin accordingly and read the changelog on every minor upgrade.
  • Security fixes target the latest 0.x release only, and there is no long-term-support branch before 1.0.
  • Ownership is enforced by dropping the write and warning in development, not by throwing. A mistake is reported rather than prevented.
  • The checks record what the team declared. They do not decide whether a declared purpose or legal basis is lawful.

What we are asking for

Agree that one feature trials it for a few weeks, then judge from its ownership report whether to extend it.
