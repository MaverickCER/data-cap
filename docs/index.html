Data, owned

Your application's data should have an owner.

data-cap treats a piece of application data — its fields, and the getters/mutators/subscriptions that acquire, mutate, or continuously observe it — as one capability-owned contract, independent of whatever database, transport, framework, or state-management library is on the other end.

You keep everything you have. No database change, no transport change, no state-management library to rip out — data-cap doesn't replace TanStack Query, Redux, Zustand, or a plain fetch-and-useState; it sits underneath, or next to, whichever of those you're already using.

One call, batteries included 
npm install data-cap
npx data-cap init

Why it exists

Fetching and state libraries answer different questions.

A fetching library dedupes requests. A state-management library gives you a store. Neither one answers:

  • Which piece of application data does this component actually own, versus merely consume?
  • Is this mutation's optimistic value going to silently disagree with what two other components expect?
  • Which capability is this subscription's transport shared with, and does tearing one down affect the other?

The cost of not answering them

As soon as more than one consumer — two components, a client and a server, two teams — needs to agree on the shape of a piece of data and its current status, that agreement usually ends up re-derived independently in each place, with no single source of truth for what "loading" or "stale" means. data-cap makes the agreement itself the artifact: a capability declares its fields and the operations that touch them, and every consumer reads the same synchronously-available snapshot.

How it works

Full manual control, or batteries included — same primitives.

buildData + createDataStore + coordinator are the same Stable primitives createData composes — start wherever matches how much control the capability actually needs.

The same Stable primitives can be composed manually for full control, or used through createData for a batteries-included dedup, status, and optimistic-mutation lifecycle.

  1. Capability schema
    1. Manual path (Stable)
      1. buildData
      2. createDataStore
      3. coordinator — full control over execution, retry, caching
    2. Batteries-included path (Experimental)
      1. createData
      2. dedup, per-operation status, optimistic mutation lifecycle
      3. Synchronously-readable snapshot

Neither path is "the" way — pick per capability. Fields are always synchronously readable from the moment buildData()/createData() returns, with no throw-until-ready gate; info is mandatory on every DataState, so consumers never special-case whether metadata has been allocated yet.

Why not just TanStack Query, Redux, or manual fetch-and-state?

You keep all of them.

data-cap doesn't replace your transport or your store — it adds the layer none of them cover.

Where common approaches stop and data-cap begins
Tool What it solves What it doesn't
Manual fetch + useState Gets data on screen No shared status vocabulary, no dedup, no optimistic-update contract — every component re-derives its own version
TanStack Query Fetching, caching, request dedup Says nothing about mutation-driven data your app owns outside a query, or how two consumers agree on ownership
Redux / Zustand / a global store One shared place to put state Doesn't distinguish declared ownership from incidental access — anything can write anywhere

See tanstack-query-integration for TanStack Query driving fetch/cache/dedup while its results flow into a data-cap store. What data-cap adds is the layer none of the above cover: one capability-owned contract every consumer reads the same synchronous snapshot from, plus a static-analysis pass that turns it into ownership and dependency evidence.

Adoption

From manual control to batteries-included.

Most applications start with whichever primitive matches how much control a capability needs — full manual control (buildData + createDataStore + coordinator) or the batteries-included createData. Neither is "the" way; pick per capability, and migrate one capability at a time.

You probably don't need it when

Your application is small, one team owns the entire data layer, and there's little reason to separate business capabilities from their storage/fetching implementation. A conventional fetch-and-useState pattern, or your existing state-management library alone, may be simpler.
