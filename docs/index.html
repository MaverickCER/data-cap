Data, owned

Declare who owns your app's data and how it may be handled.

You declare each piece of data once, in a capability: its fields, and the functions that load, change or watch them. documentData() adds its owner and each field's sensitivity, purpose, legal basis and retention.

The ESLint plugin and a build pass check your code against those declarations. The same pass writes the field catalog and ownership report, and the --check mode of the script data-cap init scaffolds fails CI when a committed copy is stale.

Lint and build checks enforce those rules, and the data documentation regenerates from your code, so it never falls behind.

Pre-1.0 · v0.10.1 · MIT

Quick start 
npm install data-cap
npx data-cap init

data-cap sits under or next to TanStack Query, Redux, Zustand or plain fetch and useState. No database, transport or state-library change is needed.

Why it exists

Fetching and state libraries answer different questions.

A fetching library dedupes requests, and a state library gives you a store. Neither says who owns a piece of data or how it may be handled. Neither keeps the page that documents it current.

Where the answers live today: a wiki page about who owns which data, each component's own idea of "loading" and "stale", a review document that lists where sensitive fields go — none of them is checked against the code.

  1. Where the answers live today
    1. a wiki page about who owns which data
    2. each component's own idea of "loading" and "stale"
    3. a review document that lists where sensitive fields go
  2. → none of them is checked against the code

data-cap writes those answers down once, in the capability that owns the data. Lint and build checks compare them with the code, and the documentation is generated from it.

How it works

Full manual control, or batteries included: same primitives.

buildData, createDataStore and a coordinator from createCoordinator are the same Stable primitives createData composes. Start wherever matches how much control the capability needs.

The same Stable primitives can be composed manually for full control, or used through createData for a batteries-included dedup, status, and optimistic-mutation lifecycle.

  1. Capability schema
  2. → Manual path (Stable): buildData · createDataStore · createCoordinator, with full control over execution, retry and caching
  3. → Batteries-included path (Stable): createData, with dedup, per-operation status and an optimistic mutation lifecycle
  4. → A synchronously readable snapshot

Neither path is the one way: pick per capability. Fields are readable from the moment buildData() or createData() returns. info is on every DataState, so components never check whether metadata exists.

What it holds to

What it holds to, and where that stops.

Each claim states its scope and links to the document that defines it, so you can check the boundary before you rely on it.

Ownership is enforced by dropping the write and warning in development, not by throwing.Scope: An unowned write is dropped and reported in development, instead of crashing the application. The warning never includes the value (tested for a string value on the createData path). data-cap is not an authorization or encryption system.Read the security model ↗

The two-module-system hazard is checked and documented.Scope: It applies when a dependency tree loads the package as both ESM and CommonJS, which creates two coordinator instances. A test pins the result: each stays correct, and dedup stops crossing between them.Read the security model ↗

Why not TanStack Query, Redux, or manual fetch-and-state?

You keep all of them.

data-cap does not replace your transport or your store. It adds one capability per piece of data, naming its owner and how it may be handled, and every component reads it. Lint and build checks compare it with the code.

Where common approaches stop and data-cap begins
Tool What it solves What it doesn't
Manual fetch + useState Gets data on screen No shared status values, no dedup, no shared optimistic-update rules; every component re-derives its own version
TanStack Query Fetching, caching, request dedup Says nothing about mutation-driven data your app owns outside a query, or how two components agree on ownership
Redux / Zustand / a global store One shared place to put state Doesn't distinguish declared ownership from incidental access; anything can write anywhere

Adoption

From manual control to batteries-included.

Most applications start with whichever primitive matches how much control a capability needs: full manual control (buildData, createDataStore, createCoordinator) or the batteries-included createData. Neither is the one way.

One capability at a time

  1. Pick the primitive that fits one capability.
  2. Migrate the next capability when it needs more control or less boilerplate. Each is independent.

You probably don't need it when

Your application is small, one team owns the entire data layer, and there's little reason to separate business capabilities from their storage or fetching implementation. A conventional fetch-and-useState pattern, or your existing state-management library alone, may be simpler.
