# Next.js example

A deliberately minimal todo app demonstrating a real user/admin data-ownership
authorization model, using only `data-cap`'s published API — never a private
`src/` import.

Unlike the [three tiers](../README.md) (which grow one work-management system
from an individual developer's project to an organization's), this is a
framework-integration example: the point isn't the capability-composition
story those three tell, it's proving `data-cap`'s client-side `createData()`
capability works correctly inside a real Next.js app, wired to a real
server-side authorization boundary — and documenting what that actually took,
including a real bug found while building it.

```
src/
  features/todos/
    data.schema.ts       <- createData + documentData, one schema for both
  lib/
    session.ts           <- "server-only"; signed demo-login cookie
    store.ts             <- in-memory todos + three seeded demo users
  app/
    page.tsx              <- server component; reads the session cookie
    todo-app.tsx           <- "use client"; useSyncExternalStore(todoData...)
    api/
      session/route.ts     <- POST (sign in), DELETE (sign out)
      todos/route.ts        <- GET/POST/PATCH/DELETE; the real authorization logic
  generated/
    data.manifest.ts      <- generated, do not edit
docs/
  DATA.md                 <- generated
  OWNERSHIP.md            <- generated
  data.evidence.json      <- generated, the full EvidenceModel
```

## The authorization model

Three seeded demo users: `alice`, `bob` (both `role: "user"`), and
`carol-admin` (`role: "admin"`). `POST /api/session` is a demo login switcher
(no password — real authentication is out of scope; real, **server-enforced
authorization** once a session exists is the point).

`GET /api/todos` is where the actual model lives:

- A regular user always gets `listOwnTodos(user.id)` — their own todos, never
  anyone else's, with no way to ask for more.
- An admin gets the same own-only view **by default**. Seeing everyone's
  todos requires an explicit `?all=true` query parameter — a real, visible
  request for the elevated view, not a silent default a future change could
  widen by accident. Requesting it without the admin role is a 403.
- `PATCH`/`DELETE` enforce ownership the same way, in `store.ts`'s
  `toggleTodo`/`deleteTodo`: the owner, or an admin, or the todo doesn't
  exist as far as the response is concerned — a non-owner gets the same 404
  either way, so a user can never learn a todo id exists just by trying to
  modify it.

Verified directly against a running server, not just read in the source:
Alice can read and modify her own todo; her request for `?all=true` gets a
403; her attempt to delete Bob's todo gets a 404 (not 403 — she can't
distinguish "not yours" from "doesn't exist"); Carol's default view is
empty (she owns no todos herself); Carol's `?all=true` view shows every
user's todos and lets her delete any of them.

## `data-cap`'s own field-documentation

`data.schema.ts`'s `documentData()` call declares the `todos` field's
`sensitivity`, `protections`, `retention`, and `purpose` — the same
declared/governance metadata the [top-level flagships](../README.md) use, now
attached to a field whose real per-record ownership is enforced by the route
handlers above, not by `data-cap` itself. `docs/OWNERSHIP.md` (regenerated by
`npm run docs`) documents this explicitly: `data-cap`'s ownership model is
capability-level (which *team* owns this field), not per-record (which *user*
owns this row) — the per-record enforcement this example exists to prove is
real application authorization code, verified by actually running it, not a
claim `data-cap`'s static analysis makes on its own.

**Known, real limitation, not silently worked around:** `npm run check`
reports one warning, `UNCONSUMED_FIELD` on `todos` — `data-cap`'s dependency
scan recognizes a literal `x.fields.Y` or `x.getSnapshot().fields.Y` read at
the call site, but not `todo-app.tsx`'s `useSyncExternalStore(todoData.subscribe,
todoData.getSnapshot, todoData.getSnapshot)` pattern, where `getSnapshot` is
passed by reference rather than called and dereferenced in one expression.
The field genuinely is read and displayed; this is a real gap in what the
static scan can see through, not a bug in this example. Documented here
rather than papered over with a redundant, unused direct read added only to
satisfy the checker.

## What it took to get `next start` actually working

Two real, empirically-found issues, both the same underlying cause as the one
[env-cap-nextjs's README](https://github.com/MaverickCER/env-cap/tree/main/examples/nextjs-app)
documents: Turbopack code-splits this app into separate chunks (the
`/api/session` route, the `/api/todos` route, the `/` page), each getting its
own separately bundled copy of any module with module-level state.

1. **`useSyncExternalStore` needs a third argument for SSR.** Without
   `getServerSnapshot` (the third argument), React throws `Missing
   getServerSnapshot, which is required for server-rendered content` and
   silently falls back to client-only rendering — confirmed directly in the
   server log. `todoData.getSnapshot` is safe to pass for both arguments: it
   reads the capability's own in-memory state, never `window`/`document`.
2. **A per-process random secret isn't actually per-process under a
   bundler.** `session.ts` originally generated `SESSION_SECRET` with a plain
   module-level `const randomBytes(32)`. Logging it from both `/api/session`
   and `/` in the same running server printed two *different* values — each
   route's separately bundled copy of `session.ts` ran its own
   `randomBytes()` call. A cookie signed by one chunk silently failed
   verification by another, with no thrown error (worse than
   env-cap-nextjs's version of this same class of bug, which at least
   crashed loudly): every request looked "not signed in" no matter how
   recently you'd logged in. Fixed by keying the secret off `globalThis` via
   `Symbol.for(...)` — the one thing every chunk in the same process
   genuinely shares — instead of module-level state a bundler can duplicate.

## Run it

```bash
npm install
npm run build
npm start
```

Then visit `/`, sign in as any of the three seeded users, and try the
authorization boundaries above for yourself — or drive them directly:

```bash
curl -c alice.txt -X POST -H 'content-type: application/json' \
  -d '{"userId":"alice"}' http://localhost:3000/api/session
curl -b alice.txt 'http://localhost:3000/api/todos?all=true'   # 403
```

## What's out of scope

Real authentication (passwords, OAuth), a real database, and CSRF protection
are all deliberately out of scope — this example exists to prove the
user/admin data-ownership boundary, not to be a production todo app. The
in-memory store (`store.ts`) resets on every server restart.
